# 上游版本与云镜像修订号：自动更新方案

状态：**方案，尚未实现**。当前仍为完整源码手动构建、逐镜像验收和 CIS 维护升级；
没有新增 CI/CD、自动晋级或改变用户的自动更新偏好。

## 版本与归属

界面分开显示「Cindy 0.1.108」和「云镜像修订 7」，详情附镜像 digest、源码提交和构建时间。
这两个数字分别回答应用来自哪个上游版本、云适配与依赖更新了几次；示例数字不代表本方案
已经给现有 R7 产物授予正式版本身份。

| 字段 | 规则 |
| --- | --- |
| `upstreamVersion` | 固定的上游正式版本，如 `0.1.108`，同时记录上游 tag 对应的 commit |
| `cloudRevision` | 同一上游版本内从 1 起递增的整数；云补丁、系统依赖、桌面、字体或启动器变化都递增 |
| `channel` | `candidate` / `canary` / `stable`，与版本顺序分开；晋级复用同一产物，不重新构建 |
| `imageDigest` | 最终 Registry manifest digest，部署身份与失败屏蔽依据；不使用本地 image ID |
| `region`、`platform` | 发布目标；CN/Global、amd64/arm64 各自验收，不能相互替代 |

客户端 `package.json` 保留真实上游版本，云版本作为独立构建元数据；普通桌面客户端继续
走现有更新器。云实例关闭应用内自更新，由 CIS 更新整个镜像，避免应用与桌面/Agent/helper
依赖分离。云设置页显示的是云端实际运行版本，不能用控制端自身的版本推算。

镜像标签可读地组合为 `0.1.108-cloud.7-cn-amd64`，但只作查找入口。CIS 从经过校验的
发行记录读取两个字段，**不对整个标签做 SemVer 排序**。SemVer 的 `-suffix` 是预发布版本，
`+metadata` 不参与优先级比较，均不适合作为这里的云修订排序规则。
依据：[SemVer 2.0.0 §9–11](https://semver.org/#spec-item-9)。

## 更新目标怎么选

先过滤同区域、架构、订阅通道、运行契约和数据迁移兼容的已准入产物，再比较
`(upstreamVersion, cloudRevision)`：先比较上游的数字三元组，相同才比较云修订整数。

| 当前 → 候选 | 自动更新决策 |
| --- | --- |
| `0.1.108 / 7` → `0.1.108 / 8` | 合格且满足维护条件时升级 |
| `0.1.108 / 7` → `0.1.109 / 1` | 新上游的云适配、迁移及目标环境验收通过后才升级 |
| `0.1.109 / 1` → `0.1.108 / 99` | 不自动降级 |
| 相同版本对、不同 digest | 拒绝，版本不可覆盖；修订号必须递增 |
| 相同 digest | 不重启、不重复备份或升级 |
| 未登记、撤回、失败屏蔽或缓存未就绪 | 不升级，明确展示等待原因 |

Registry 出现更高 tag 只表示存在候选，不等于发布授权。不能只取全仓最高 tag 再检查准入：
应在合格发行记录中选择最高兼容版本，避免一个未验收版本挡住其他已合格更新。
版本比较只决定新旧；没有兼容声明时，即使数字更大也不能自动跨越数据/运行契约变化。

新认领默认与存量自动更新读取同一份区域/架构稳定通道记录。通道更新通过带版本条件的
原子操作发布；认领及维护操作创建时保存精确 digest 和发行记录版本，执行中不跟随
`latest` 或可变 tag。租户专属 pin 必须显式展示，不能静默覆盖全局稳定通道。

## 构建、准入和升级

`cindy` 客户端仓负责完整 Dockerfile、冻结依赖、构建审计、隔离验收、发布，以及主镜像和
**全部实际 initContainer 镜像**在目标 Region/网络的 ACS Ready 与命中证据。
发行记录同时绑定源码、配方、依赖锁摘要、运行契约版本、init 镜像集合、验收报告和缓存证据。
仅信任配置的发行来源，不能把任意 Registry 标签或镜像自报 label 当成已验收版本。

`cindy-server` 中的 CIS 消费合格发行记录，负责身份和模板校验、任务保护、停机只读加密
OSS 备份、升级、健康验收与失败恢复。构建侧不获取业务 PVC；CIS 不构建镜像或创建缓存。
工作分支分别是客户端 `feat/cloud-settings-native-client` 和服务端
[`feat/cloud-settings-readonly`](https://github.com/zhuoshaojian/cindy-server/tree/feat/cloud-settings-readonly)。

发布顺序：源码/依赖冻结 → 完整构建 → 隔离 Linux 验收 → 发布候选 digest → 全部镜像缓存
就绪及命中 → 本人实例灰度验收 → 稳定通道准入 → 新认领与存量按策略消费。
上游新版本检测可自动创建构建候选，但不能跳过云适配和晋级检查直接切生产。

存量保留原自动更新开关、维护窗口与定时任务。运行中实例先确认空闲及近期任务保护，
停机备份成功后切换，备份失败则终止。停止实例不唤醒：支持的只读冷备份完成后只更新
下次启动模板；没有合格冷备份路径时显示等待，不绕开备份也不伪造停机凭据。
按 Region/集群限制并发、错峰扫描，实例锁与操作记录幂等，不能依赖单进程内的锁保障全局。

失败按 digest 屏蔽后续自动尝试，暂停该发布批次，保留恢复操作。回滚是显式、有审计的
恢复操作，不经过“自动选择更高版本”通道；新程序可能写入数据后必须遵守备份恢复与数据
兼容规则，不能仅换回旧镜像。已完成操作重启控制面后不重放业务写入。

## 分步落地与验收

1. **发行元数据与 UI**：客户端构建产出两个版本字段及来源；CIS 记录期望和实际版本，
   客户端云设置显示实际版本/目标版本/等待原因。跨仓字段以可选字段兼容旧端，不改变旧
   `image` 字段含义；字段缺失显示未知，不能编造修订号。
2. **统一选择器**：替换 CIS `registry-tags.ts` 的纯 `X.Y.Z` 筛选，以及
   `maintenance-scanner.ts`、`orchestrator.ts` 的各自比较路径；已接入维护、旧实例、
   停止实例和新认领都使用同一准入规则。旧路径不能靠发布 tag 绕过白名单或备份。
3. **历史映射与切换**：按实际 digest 显式登记现存产物的版本对；历史 `rN`/日期不能自动
   推断为正式修订。先部署只读元数据和兼容选择器、校验各环境，再切稳定通道。
   旧控制器不认识的新标签维持不自动升级；不为了兼容旧扫描器额外推纯 `X.Y.Z` 标签。
4. **后续 CI/CD**：在上述本地构建和准入接口已验证后，接入自动候选构建、缓存准备、
   人工或策略批准晋级、分批升级与失败暂停。现阶段这些流水线均未实现。

至少覆盖同上游修订升级、跨上游升级、拒绝降级、同版本换 digest、失败版本屏蔽、
缺失/过期缓存、Region 差异、旧客户端降级展示、并发认领/晋级、控制面重启恢复、忙碌任务
延期、停止实例不唤醒、备份失败及迁移后回滚。自动化测试、真实云端验证和手机真机验收
分别记录，不互相代替。
